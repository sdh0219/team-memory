# team-memory token benchmark：接手开销实测

> 一个没装记忆层的仓库，新 agent 冷启动要读多少 token？装了 team-memory 呢？
> 本文给出可复现的实测数字。

## 结论先看

| 场景 | 读取内容 | 实测 token | 倍率 |
|---|---|---|---|
| ❄️ 无记忆层（冷启动通读） | susu-tools 全部 261 个文本文件 | **447,024** | — |
| ⚡ team-memory 接手 | 只读 `.memory/STATE.md`（≤50 行活文档） | **221** | **≈ 1/2000** |
| team-memory 仓库自测 | 自身 24 个文件 vs 自己的 STATE.md | 8,384 vs 221 | ≈ 1/38 |

冷启动的 44.7 万 token 不是一次性开销——**每个新会话、每个换班的 agent 都要重烧一遍**。
team-memory 把它变成一次 221 token 的读取，且这个数字被协议钉死在 50 行以内，不会随项目膨胀。

## 口径与复现

```bash
python scripts/benchmark.py                    # 测本仓库
python scripts/benchmark.py --repo <任意git仓库>
```

- **无记忆层侧**：`git ls-files` 列出的全部文本文件（.md/.ts/.py/.json/.yml 等 20+ 种扩展名）全部读入。
  这是"agent 想搞清楚项目现状"的保守下界——真实操作中还要读依赖文档、跑探索性搜索，只会更多。
- **team-memory 侧**：只计 `.memory/STATE.md`（协议规定接手者必读且唯一必读）。
  LOG.md / git log 属于"按需深读"，不计入接手开销。
- **token 估算**：CJK 字符按 1 token/字，其余按 3.8 字符/token（GPT 系分词器的常见比例）。
  这是近似口径，不是某家 API 的精确计数；对结论的量级（约 2000 倍）没有影响。

## 为什么这个对比是诚实的

- 冷读侧**没有**多算：没把二进制、锁文件算进来；也没把 agent 实际会做的多轮探索搜索算进去。
- 记忆侧**没有**少算：STATE.md 是协议规定的完整必读内容；221 token 是实测本仓库自己的 STATE.md 得到的。
- 项目越大，差距越大：susu-tools 只是 261 个文件的中型项目；上千文件的项目，冷读侧是百万级。

## 局限

- 估算口径与真实分词器有 ±20% 以内的偏差，不影响量级结论。
- "冷启动是否真的通读全部文件"取决于 agent 的策略——但任何足够认真的接手都需要覆盖核心代码与文档，
  通读是最常见的策略下界。
- 记忆层的隐性成本（收工时写 STATE/LOG 的 token）未计入：一条 LOG ≤10 行、STATE ≤50 行，
  写入成本约为一次冷读的 1/1000 量级。
